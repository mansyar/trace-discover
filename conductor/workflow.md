## Guiding Principles

1. **The plan is the source of truth.** Every phase, task, result, checkpoint and
   evidence link lives in `plan.md`.
2. **The tech stack is deliberate.** A stack change is recorded in
   `tech-stack.md` before the implementation depends on it. `trace-discover`
   ships zero runtime dependencies beyond `@rive-app/canvas-lite`, no network at
   runtime, and no new shipped assets without a budget re-record.
3. **Verification is agent-executed.** The phase agent runs the configured checks
   and writes the evidence. The user is not asked to verify routine work; they are
   asked for credentials, hardware and external approvals only.
4. **Evidence over assertion.** A phase is complete only when the configured
   checks pass and the evidence file exists.
5. **No silent debt.** A finding is fixed, explicitly accepted with a reason, or
   tracked as an issue. Strict review: nothing is deferred unseen.
6. **Stay inside the phase contract.** `Touches` is the expected blast radius; a
   required deviation is allowed, recorded, and reviewed.
7. **Phones are the contract.** Every layout change must leave both phone
   references (430×860 portrait, 860×430 landscape) pixel-identical unless the
   track's spec says otherwise, and every probe carries both references.
8. **Non-interactive and CI-aware.** Prefer commands that terminate; use `CI=true`
   for watch-mode tools.

## Workflow Config

```yaml
project:
  type: "browser game (static offline-first PWA)"
  languages: ["TypeScript", "CSS", "HTML"]
commands:
  setup: "pnpm install && (cd dev && pnpm install)"
  dev: "pnpm dev"
  test: "CI=true pnpm test"
  coverage: "CI=true pnpm test --coverage"
  lint: "pnpm exec biome check ."
  format: "pnpm exec biome format --write ."
  typecheck: "pnpm exec tsc --noEmit"
  build: "pnpm build"
  verify_phase: "CI=true pnpm check && pnpm pack:check && CI=true pnpm test --coverage && pnpm build && pnpm budget"
coverage:
  gate: { statements: 72, branches: 76, functions: 88, lines: 72 }
  scope: "project"
verification:
  layers: ["static", "unit", "build", "budget", "smoke", "visual", "manual"]
  retry: 2
  manual_exceptions:
    - "iPad and Android tablet device passes (hardware)"
    - "Cloudflare API token and account id for a release"
    - "GitHub CLI authentication before a PR"
git:
  base_branch: "master"
  fetch: true
  commit_style: "conventional"
  task_commits: true
  phase_squash: true
review:
  strict: true
  issues:
    enabled: true
    auto_create: false
    min_severity: "low"
    group_low: true
    labels: ["tech-debt", "conductor"]
pr:
  enabled: true
  tool: "gh"
  base: "master"
  media: "always"
  watch_ci: true
  watch_timeout_minutes: 15
  merge_method: "squash"
```

**Why these values.** The coverage gate is the one already enforced in
`vite.config.ts` (statements 72, branches 76, functions 88, lines 72) and applies
to the whole project, so new modules must land well above it. `verify_phase` is
the CI gate minus the smoke step, which needs a live preview server.
`review.strict: true` means every finding is fixed, accepted only with an
out-of-scope reason, or filed as an issue — the batch is shown for confirmation
before anything is filed. `pr.media: always` reflects that this is a visual
product: a capture of the affected flow goes in the PR body, which needs `gh`
2.99.0 or later (installed here: 2.103.0). `watch_ci: true` with a 15-minute cap
keeps the merge gate honest on a CI run that takes about a minute.

## Phase & Task Workflow

Implementation runs one phase at a time. The primary agent owns `plan.md`,
`metadata.json`, the registry, `review.md` and the PR; the phase work is done in
the current worktree and verified before it is accepted.

### Task Lifecycle

1. Read the phase contract in `plan.md`, the requirement IDs in `spec.md`, and the
   applicable guides in `conductor/code_styleguides/`.
2. Write or update the failing test first (this project is test-first), then the
   smallest implementation that passes it.
3. Run the targeted checks for the task.
4. Commit the task with a conventional message; attach a `git notes` summary to
   the commit (kept from the v1 workflow as an extra audit trail — the committed
   verification report remains the primary evidence).
5. Report the task's status and commit SHA to the primary agent, which marks the
   task complete in `plan.md` after it accepts the phase.

### Deviations

- If the phase goal requires a file outside `Touches`, make the smallest
  necessary change and record it in the phase's evidence under `Deviations`.
- If the work needs a product, design or hardware decision, stop and report
  `blocked` — do not invent the answer.
- Do not silently expand scope, add a dependency, add a shipped asset, or migrate
  unrelated code.

### Phase Completion

1. Run the phase's `Verification` command exactly as written in `plan.md`.
2. Run `verify_phase` when it is different from the phase command.
3. Write the evidence file at the path in `## Verification Strategy`.
4. Return the structured report; the primary agent updates `plan.md` with the
   result, checkpoint SHA and evidence link.
5. The agent does not merge, rebase, reset, push, open a PR, or edit Conductor
   state files. Pushing, the PR, and the archive commit belong to the primary.

### Review Fixes

A review that finds actionable issues appends a `Phase R<n>` to `plan.md`. Fixes
go through the same loop — red test, fix, evidence, checkpoint — and the review
is re-run against the fix delta (at most two rounds). See
`conductor-review` for the loop.

## Verification Strategy

### Layers

- **Static** — Biome (lint + format check) and `tsc --noEmit`.
- **Data** — `pnpm pack:check`: every pack JSON validates against the schema.
- **Unit** — Vitest over logic, layouts, session, renderer painters and stores.
- **Build** — production `vite build`, including the generated service worker.
- **Budget** — `pnpm budget`: dist bytes and precache entry count.
- **Smoke** — `dev/qa/qa-smoke.mjs` against the built app: boot → `pre-1` →
  success with zero page errors (runs in CI on every PR).
- **Visual / flow probes** — the Playwright probes under `dev/qa/`, driven by the
  built app. The canonical ones are listed in `dev/README.md`; run the ones the
  track touches (`qa-tablet`, `qa-landscape`, the pack sweeps, zero-text,
  offline, perf). Screenshots land in `dev/qa/out/` (gitignored).
- **Manual (human-only)** — device passes on an iPad and an Android phone/tablet,
  and the release secrets. Everything else is executed by the agent.

### Commands

| Layer | Command | Required |
| --- | --- | --- |
| static | `CI=true pnpm check` | yes |
| data | `pnpm pack:check` | yes |
| unit | `CI=true pnpm test --coverage` | yes |
| build | `pnpm build` | yes |
| budget | `pnpm budget` | yes |
| smoke | `pnpm preview --port 4173 &` then `node dev/qa/qa-smoke.mjs` | yes in CI |
| visual | `node dev/qa/<probe>.mjs [url]` from `dev/` | when the track touches that surface |
| visual | `PORT=4173 node dev/qa/qa-landscape.mjs` | when layout or field code changes |
| perf | `node dev/qa/qa-perf.mjs http://localhost:4173/ pre-1` | when render or asset weight changes |

### Services and Fixtures

- **Preview server:** `pnpm preview --port 4173` (production build) — the default
  base URL for probes is `http://localhost:4173`. On this host Vite binds `::1`,
  so use `localhost`, not `127.0.0.1`. CI uses `pnpm preview` on the same port.
- **Dev server:** `pnpm dev` (`:5173`); several probes default to a dev port
  (`:5199`, `:5176`) and take a URL argument or `PORT` env var instead.
- **LAN server:** `pnpm serve --host --port 4173` — real-device passes. Devices
  must be on the same network; reload twice or use a private tab, or the service
  worker will serve the previous build.
- **Browser:** `playwright-core` driving Microsoft Edge
  (`channel: 'msedge'`), no bundled browser download.
- **Fixtures:** probes seed `localStorage['trace-discover-save-v1']`
  (schema v3: `badges`, `completedLevels`, `settings`, `name`) before boot. The
  menu is progressive, so screens that show every pack seed a six-pack save.
- **Environment variables:** none at runtime. Release only:
  `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID` (repo secrets).

### Pass Criteria

- Every required command exits `0`.
- Coverage meets the enforced thresholds (72 / 76 / 88 / 72) for the project.
- Every acceptance criterion in `spec.md` has a test or a documented evidence
  artifact.
- The phone references are unchanged unless the spec says otherwise.
- No Critical or High review finding remains unresolved; no finding is silently
  deferred.

### Evidence

Write one committed report per phase:

```text
conductor/tracks/<track-id>/verification/phase-<n>.md
```

Include: title; track, phase, date, branch and head commit; result (`verified`,
`failed`, `blocked`, `partial`); a commands table (layer, command, exit, summary);
an acceptance-criteria table (ID, criterion, evidence, status); evidence paths
(commit SHAs, probe logs and screenshot directories); deviations; notes. Put
binaries, screenshots and large reports under `.conductor/evidence/` — that path
is gitignored. Probe screenshots already land in the gitignored `dev/qa/out/`.

### Fallback Ladder

1. Run the full configured layer.
2. If the preview server is not up, start it (`pnpm preview --port 4173`) and
   poll `http://localhost:4173/index.html` before running the probe.
3. If a probe still cannot run, run the narrowest reliable subset and mark the
   phase `partial` with the reason.
4. Stop and ask the user only for credentials, hardware (device passes) or an
   external approval.

### Retry Policy

- A failed check may be fixed and re-run at most **2** times.
- If it still fails, report `failed` with the command and the output.
- Never mark a phase `verified` when a required check did not run.
- A stale probe that fails on its own baked-in expectation is fixed as a
  deviation (recorded in the evidence), not worked around.

### Human-Only Exceptions

- The iPad / Android tablet / phone device pass (hardware and a soft keyboard).
- `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` for a release.
- `gh` authentication before a PR is opened.

## Quality Gates

Before a phase is accepted:

- [ ] Required tests pass; new logic is test-first
- [ ] Coverage gate met (72 / 76 / 88 / 72)
- [ ] Biome and `tsc --noEmit` clean
- [ ] `pnpm pack:check` passes (if pack data changed)
- [ ] Build passes and `pnpm budget` stays within 6.0 MB / 200 entries
- [ ] Code follows `conductor/code_styleguides/`
- [ ] Phone references unchanged, or the spec records why not
- [ ] No secrets, credentials or PII introduced; no runtime network calls
- [ ] Public behaviour documented when it changed (`product.md`, `tech-stack.md`,
      `dev/README.md` as applicable)
- [ ] Evidence written and linked from `plan.md`

## Code Review Process

The self-review checklist before asking for review:

1. **Functionality** — feature works as specified; edge cases handled; no
   dead-ends for a toddler.
2. **Code quality** — follows the style guides; no duplication; names say what
   the thing is; comments explain the *why*.
3. **Testing** — unit tests cover the logic; the relevant flow probes run; new
   modules are near 100 % covered.
4. **Security** — no secrets in code or logs; no runtime network; stored saves
   are sanitized on load.
5. **Performance** — frame time stays inside the recorded envelope; no new asset
   without a budget note.
6. **Phones and tablets** — both phone references unchanged; every tablet space
   checked when layout moved.

`conductor-review` runs this track-level, records findings by severity with the
file and line, and appends a fix phase for anything actionable.

## Testing Requirements

### Unit

- Every module has a matching `*.test.ts` beside it.
- Test the failure and edge cases, not just the happy path.
- Deterministic: no timers, no randomness without a seed, no real canvas.

### Integration / Flow

- Prove complete flows with a probe when a change spans screens: boot → menu →
  pack → level → success → badge, plus the parent zone where it applies.
- Seed saves rather than clicking through unlock ladders.

### On-Device

- Device passes are the only manual layer: real touch, a real soft keyboard, and
  a pixel comparison against the shipped baseline.
- Serve the production build over the LAN (`pnpm serve`), never the dev server.

## Commit Guidelines

### Message Format

```text
<type>(<scope>): <description>

[optional body]

[optional footer]
```

### Types

- `feat`: new feature · `fix`: bug fix · `docs`: documentation only ·
  `style`: formatting · `refactor`: behavior-preserving change · `test`: tests
  only · `chore`: maintenance

### Examples

```bash
git commit -m "feat(field): add the 4:3 tablet design space"
git commit -m "fix(mascot): size the tap zone from the drawn sprite"
git commit -m "test(parentZone): cover the keyboard inset clamp"
```

Task-level commits carry a `git notes` summary. The primary agent adds the plan
state commit (`conductor(plan): ...`) and the review/archive commits
(`conductor(review): ...`, `chore(conductor): Complete and archive track ...`).

## Definition of Done

A track is complete when:

1. Every phase is `verified` with a checkpoint and evidence.
2. The integrated verification on the track branch passes.
3. Review is `PASS`, or every finding is fixed, accepted with an out-of-scope
   reason, or tracked as an issue. No Critical or High finding is unresolved
   without an explicit override recorded in `review.md`.
4. Post-review documentation sync is complete (`tech-stack.md`, `product.md`,
   `dev/README.md`, and the metadata `doc_sync` field).
5. The registry and `metadata.json` show the track as complete and archived.
6. The branch is pushed and a PR is open (or `pr_state: "unavailable"` records
   why it could not be), unless the user asked for a local-only delivery.
7. The device pass is confirmed by the owner when the track touches touch
   geometry, a soft keyboard, or anything the probes cannot reach.

## Emergency Procedures

### Critical Bug in Production

1. Branch from `master`; write a failing regression test first.
2. Implement the minimal fix; run the full verification strategy.
3. Open a PR immediately; do not batch unrelated work.
4. Release via a patch tag once merged (see Deployment).

### Data Loss

The app's only persistent state is the child's save in `localStorage`
(`trace-discover-save-v1`, schema v3) plus the content cache.

1. Stop writes; ship a build that stops mutating the save.
2. Restore from the last known-good schema path — never invent fields.
3. Verify a boot with a pre-existing save and with a corrupt one (the store
   sanitizes and rewrites).
4. Document the incident and the recovery path.

### Security Breach

1. Rotate the affected secrets (`CLOUDFLARE_API_TOKEN`, `gh` token).
2. Review the release and Actions logs for unauthorised runs.
3. Patch, re-release, and document the incident.

## Deployment

All of this is automated by `.github/workflows/ci.yml` (checks) and
`.github/workflows/release.yml` (releases). Tags are the release trigger; the
only human decision is the version.

### Pre-Release Checklist

- [ ] `master` CI is green (Actions → CI)
- [ ] `package.json` version bumped and committed (`chore(release): <version>`)
- [ ] Tag name matches `package.json` exactly (`v<version>`, strict semver) — the
      Release workflow refuses to run otherwise
- [ ] Repo secrets present: `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`

### Release Steps

1. Bump `package.json` to the release version and push to `master`
   (`chore(release): <version>`).
2. `git tag -a v<version> -m "<version>"` (prereleases like `1.0.0-rc.1` are
   allowed — use them for release candidates).
3. `git push origin v<version>` — this triggers the Release workflow.
4. Observe the run (Actions → Release): guards → checks → tests → build → Pages
   deploy → GitHub Release.
5. Verify: the run is green; the Release exists with generated notes and a
   "Deployed at …" line; the URL serves the app.
6. Stable tags deploy to production (`trace-discover.pages.dev`, branch
   `master`); prerelease tags deploy only to the `rc` preview
   (`rc.trace-discover.pages.dev`).

### Rollback

- **Bad deploy, good code:** promote the previous Pages deployment in the
  Cloudflare dashboard (Deployments → ⋯ → Rollback).
- **Bad code:** revert the offending commit on `master`, bump to the next patch
  version, re-tag and push — never move or delete a released tag.
- Never hand-deploy `dist/` to production; the tag path is the only sanctioned
  release route.

### Post-Deployment

1. Monitor the Cloudflare dashboard (requests, errors).
2. Check the app boots on a real device — local builds via `pnpm serve` plus the
   LAN URL; live by installing from the published URL.
3. Gather feedback and plan the next iteration (minor for features, patch for
   fixes).
